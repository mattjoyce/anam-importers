How importers fit

1. What an importer is

Anam is a personal longitudinal record: an append-only ledger of facts about one person, with everything else derived from it. It used to read each vendor's data itself, with a Go worker per source compiled into the binary that owns the ledger. Every new source meant a new release of that binary, and a parsing bug in one vendor's format ran inside the process holding the record.

An importer moves that work out. It is a ductile plugin that reads one source and shapes its rows into payloads that match a Facet Definition: a JSON Schema plus the rules for which fields identify a fact and which field says when it happened. Anam keeps the Definitions it publishes, the admission gate that checks every payload, and the record. It no longer knows any vendor's format.

Two things follow. An importer can be written in any language that can validate JSON Schema, and a broken importer can only fail to send; it cannot corrupt what Anam already holds.

2. The pieces, and who holds what

PieceHoldsDoes not hold
The importer (withings/)The source's format, and the Definitions it emits in definitions/<type>.jsonA token, Anam's address, any identity rule
anam_submitOne importer's token, granted by the gateway's vault to that instance aloneAny knowledge of a source
anam_importer, the baseLoading Definitions, local validation, batching, the HTTP client, the ductile protocolAnything vendor-specific
AnamPublished Definitions, the gate, the ledger, and each importer's token as a SHA-256 with the source and types it may useThe token itself, any vendor's format

One anam_submit instance per importer, each with its own token, so a token never leaves the plugin that uses it. The token names the source: envelopes carry no source field, and Anam admits everything a token sends as that token's source. An importer that takes over a built-in worker's data uses that worker's source name, so its facts are the same facts.

A Definition version is immutable once Anam holds it. A change to the schema is a new version, and a new version may change the schema or classification but not which fields identify a fact or say when it happened.

3. A batch's journey

  1. Shape. The importer reads the source and builds one payload per fact, using the source's own values. It composes no identity, joins nothing and summarises nothing; the gate works out identity from the Definition's identity_key.
  2. Validate. check tests every payload against its Definition's JSON Schema with a stock library. If any fails, the run fails and nothing is emitted, so a refusal at the gate later means the importer and Anam disagree about the Definition, not that a row was malformed.
  3. Batch. batches cuts the envelopes into groups of at most 49, the gate's transaction size.
  4. Emit. Each batch goes out as a <plugin>.batch event carrying the envelopes, the Definitions they were shaped to (as JSON text) and a label. A pipeline routes it to that importer's anam_submit instance.
  5. Publish. For each Definition, anam_submit asks Anam for that type at that version. If Anam holds it with the same body, it moves on. If Anam answers 404, it registers it. If Anam holds a different body at that version, it stops without retrying: the two disagree about what that version means, and nothing should be submitted until they agree. A type Anam's binary bundles is always found by the GET, so it is never registered.
  6. Post. The batch goes to POST /v1/envelopes under the token. Anam admits it whole or not at all.
  7. Report. On 200 it emits anam.admitted with the watermark w and a count of each outcome.

What the outcomes mean

OutcomeMeaning
admittedA fact Anam had not seen before.
no-opThe same payload under the same identity. Nothing written.
supersededThe same identity with a changed payload. The new version is written; the old one stays in the ledger.

4. When things fail

Every response a plugin gives the gateway says whether trying again can help. The base decides it the same way everywhere:

What happenedRetriedWhy
503 from AnamYesAnother write held the ledger for more than 5 s, usually an ingest. The same batch will land.
Other 5xx, 429, timeout, connection refusedYesThe daemon or the network, not the data.
422 batch refusedNoThe data or the Definition is wrong. The run fails with each refused envelope's reason in its logs.
401 / 403NoThe token is missing, wrong, or not allowed this type.
A Definition Anam holds with another bodyNoA disagreement someone has to settle.
Source database lockedYesThe writer will finish. Raised as Failure(..., retry=True).
Source table missing, a bug, bad configNoTrying again will fail the same way.

Sending a batch again is always safe. An unchanged payload is a no-op, so a run that is unsure whether its batch landed, because the connection dropped after the request went out, just sends it again. The same property makes resend-everything a cheap way to catch up: a full Withings resend is 113 batches, nearly all no-op.

The gateway does the retrying, under each plugin's retry: settings, so a plugin never sleeps and loops. Whatever goes wrong, a plugin still writes exactly one response to stdout, so a crash is reported as an error the gateway can act on rather than a traceback it can't.

5. Writing a new importer

  1. Make a folder named for the source, holding manifest.yaml (the ductile plugin manifest), run.py, and definitions/<type>.json for each type it emits. A Definition is Anam's manifest format: closed JSON Schema in schema, identity and time in meta.
  2. In run.py, read the source and build payloads. Wrap each with envelope, validate with check, cut with batches, and emit one event per batch.
  3. Give it a handle for whatever event announces new data, and a poll that resends everything. Anam makes the resend idempotent.
  4. Raise Failure(message, retry=...) where the source fails, saying whether a later try can help.
  5. Add a pipeline from <plugin>.batch to a new anam_submit instance, give that instance its own token in the vault, and add the token's SHA-256, source and types to Anam's importers_file.
  6. Bump the repo's version (one version for everything; a test checks every manifest agrees) and note it in the changelog.
import anam_importer as ai
from anam_importer import ductile

DEFS = ai.load(HERE)                      # definitions/*.json, by type
d = DEFS["health.measurement.withings"]

envs = [ai.envelope(d, payload) for payload in rows]
ai.check(DEFS, envs)                      # raises Invalid before anything leaves
events = [ductile.event("anam_withings.batch",
                        {"envelopes": b, "definitions": [d.body.decode()], "batch": label})
          for b in ai.batches(envs)]
return ductile.ok(f"{len(envs)} measurements", events=events)

Payloads carry the source's own values as the source wrote them. If the source says "2026-10-09 07:30", the payload says that, and the Definition's time_semantics tells Anam how to read it. Converting units, merging rows, or computing anything belongs in a projection inside Anam, not in an importer.

6. The Withings example

anam_withings reads the database the withings plugin keeps, read-only, and emits one health.measurement.withings envelope per measurement, with its measure group's attribution beside it. It runs on three triggers:

  • withings.measurement_recorded: the batch for that one new measure group.
  • withings.reconciled: everything, since a reconcile can change old groups' attribution.
  • A daily poll: everything, because the withings plugin rewrites readings Withings revises in place and announces only new groups. A correction reaches Anam within a day.

It replaces a Go worker that Anam's binary carried. Both submit under the source withings and Anam builds identity from (withings_id, type) either way, so the same measurement from either path is the same fact. During cut-over both run, and the importer's batches should come back no-op. When they do, the Go worker is deleted.

Why values are written 29.371

The withings plugin stores a value as a SQLite REAL, a binary double with no text of its own. Anam's Go worker read it with CAST(value AS TEXT), and its SQLite build writes 17 significant digits whenever 15 do not read back as the same double: 29.371000000000002. SQLite 3.43 and later write the shortest form, 29.371. So the worker's text came from its SQLite build, and an upgrade of that library would itself change it.

anam_withings writes the shortest decimal that reads back as the same double, without an exponent (0.00001, not 1e-05, which the Definition refuses). IEEE 754 fixes that text whatever language or library reads the value. Against the live record, 222 of 5,531 measurements are written differently by the two paths, each the same number. At cut-over those 222 come back superseded once, with the old text kept in the ledger, and every resend after that is no-op.

Whether to accept those 222 supersessions, or instead render each value from Withings' own integer and exponent, is still open. This page describes what 0.1.0 does.
